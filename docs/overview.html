Topologia

A mesma instância do Traefik atende as duas interfaces. O que separa público de privado não é a porta — é o IP de origem, filtrado por um middleware, sobre um endereço que simplesmente não é roteável fora da tailnet.

As quatro camadas

A linha que separa as camadas é a frequência de mudança. Isso define quem manda em cada uma: o que raramente muda é imperativo e roda uma vez; o que muda toda hora vive no Git.

01Provisionamento hardening · deploy · Tailscale · k3s · backup Ansible · 1× por servidor
02Plataforma cert-manager · Sealed Secrets · ArgoCD · KEDA · CNPG Ansible + Helm · raro
03Serviços de dados Postgres · Valkey · RustFS ArgoCD · eventual
04Projetos my-portfolio · próximos ArgoCD · a cada push

O ArgoCD não gerencia as camadas 1 e 2 por dependência circular: ele precisa do cert-manager para o próprio certificado e do repositório para saber o que aplicar. Componente que o ArgoCD precisa para funcionar não pode depender dele para existir.

Todos os três foram escolhidos por um critério explícito: sair de instância única para replicado é mudar um campo, não remontar a arquitetura.

Decisões

As escolhas que moldaram o resto, e o motivo de cada uma.

k3s, não kubeadm

2 vCPU não comportam um control plane completo. O k3s traz Traefik, storage e containerd num binário só.

API do Kubernetes fora da internet

A porta 6443 só escuta na interface da tailnet. Workers futuros entram por uma rede privada que independe do provedor.

DNS-01, não HTTP-01

Não depende da porta 80 nem de o host ser alcançável. É o que permite certificado válido para serviços que só existem na tailnet.

O CI escreve no Git, não no cluster

Nenhuma credencial de cluster no GitHub. O pior caso de um token vazado é um commit revertível.

Instâncias compartilhadas

Uma instância por projeto multiplicaria a RAM a cada projeto. Compartilhado, cada um ganha seu espaço dentro da mesma instância.

Valkey, não Redis

Os charts do Bitnami estão migrando para um repositório pago. O Valkey é o fork open-source, com a mesma API.

Sem Kafka

Um broker JVM pediria ~1,5 GB de heap — quase um quinto da máquina, disputando com todo o resto. Fica para quando houver hardware.

Root fora do dia a dia

Acesso por um usuário dedicado, com chave própria. Login root pela rede está desabilitado, e o gate de validação impede lockout.

Referência rápida

O suficiente para começar a operar.

# acesso
ssh vps                      # deploy, root fechado
tailscale up
export KUBECONFIG=.secrets/vps-1.kubeconfig

# saúde
kubectl get nodes
kubectl get applications -n argocd
kubectl get pods -A | grep -v Running
kubectl top nodes
# provisionar (idempotente)
cd ansible
ansible-playbook -i inventory/hosts.ini site.yml \
  --private-key ../.secrets/vps-1_deploy_ed25519

# forçar sync do ArgoCD
kubectl annotate application root-app -n argocd \
  argocd.argoproj.io/refresh=hard --overwrite

Deploy leva até ~3 min. Não há webhook — o ArgoCD é privado e o GitHub não alcança um endpoint dentro da tailnet. O sync é por polling, e essa foi uma troca consciente: manter o plano de controle fora da internet vale mais que instantaneidade no deploy.
